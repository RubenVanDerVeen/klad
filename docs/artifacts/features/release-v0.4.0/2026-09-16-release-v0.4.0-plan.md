# Klad v0.4.0 Release — Implementation Plan

> **For agentic workers:** Execute via `/execute-plan` conventions: orchestrator
> dispatches one executor + one reviewer per task, Conventional Commits per
> task, oracle on two-strike failures. Steps use checkbox (`- [ ]`) syntax.
> **Ponytail mode is active.**

**Goal:** Cut and publish Klad v0.4.0 as a public GitHub release with CI-built `.exe`, `.deb`, and AppImage.

**Architecture:** No code changes. Bump version in three synced files, reconcile `CHANGELOG.md`, commit on `main`, push an annotated `v0.4.0` tag; the existing `.github/workflows/release.yml` builds all artifacts into a draft release, which we verify, annotate, and publish via `gh`.

**Tech Stack:** git, GitHub CLI (`gh`), existing Tauri 2 release workflow (`tauri-apps/tauri-action@v0`), npm/vitest, cargo.

**Spec:** `docs/artifacts/features/release-v0.4.0/2026-09-16-release-v0.4.0-design.md`

## Global Constraints

- **Work directly on `main` — do NOT create a feature branch.** The tag must sit on `main`; the user explicitly approved committing and pushing `main` + tag for this release.
- Conventional Commits 1.0.0 (enforced by `.githooks/commit-msg`).
- Version canonical source: `src-tauri/tauri.conf.json` → `version`; sync targets `package.json` → `version`, `src-tauri/Cargo.toml` → `[package].version`. All three must read `0.4.0` at the end.
- Shell is Windows PowerShell 5.1: use `;` / `if ($?)` to chain, quote paths, no `&&`.
- Only approved pushes: release/docs commits to `main` and the `v0.4.0` tag. Nothing else.
- If any verification step fails **before** the tag push: stop and report; do not push.
- No changes to `.github/workflows/`, bundle config, README, or source code.

### Task 3: Tag, push, verify CI, publish release

**Files:** none modified (git/gh operations only).

**Interfaces:**
- Consumes: the two commits from Task 2.
- Produces: public GitHub release `v0.4.0` with `.exe`/`.deb`/AppImage assets and changelog notes.

- [ ] **Step 1: Tag and push**

```powershell
git tag -a v0.4.0 -m "Klad 0.4.0"; if ($?) { git push origin main }; if ($?) { git push origin v0.4.0 }
```

Expected: both pushes succeed.

- [ ] **Step 2: Watch the CI run until completion**

```powershell
gh run list --workflow=release.yml --limit 3
```

Identify the run for tag/branch `v0.4.0` and take its ID, then (allow a long timeout — builds take 5–15 minutes):

```powershell
gh run watch <RUN_ID> --exit-status
```

Expected: run completes with success exit code. **If it fails:** diagnose from `gh run view <RUN_ID> --log-failed`, fix forward on `main`, then `git push origin :refs/tags/v0.4.0`; `git tag -d v0.4.0`, re-commit fix, re-tag, re-push, and repeat this step. Do not publish anything from a failed run.

- [ ] **Step 3: Verify the draft release and its assets**

```powershell
gh release view v0.4.0 --json name,isDraft,assets
```

Expected: `isDraft: true`, assets include all three of:
- `Klad_0.4.0_x64-setup.exe`
- `klad_0.4.0_amd64.deb`
- `klad_0.4.0_amd64.AppImage`

- [ ] **Step 4: Set release notes from the changelog**

```powershell
$lines = Get-Content CHANGELOG.md; $start = ($lines | Select-String -Pattern '^## \[0\.4\.0\]').LineNumber; $end = ($lines | Select-String -Pattern '^## \[' | Where-Object { $_.LineNumber -gt $start } | Select-Object -First 1).LineNumber; if (-not $end) { $end = $lines.Count + 1 }; $notes = ($lines[$start..($end - 2)] -join "`n").Trim(); gh release edit v0.4.0 --notes "$notes"
```

Expected: "✓ Edited release v0.4.0" (or similar success output).

- [ ] **Step 5: Publish the release**

```powershell
gh release publish v0.4.0; if ($?) { gh release view v0.4.0 --json isDraft,url }
```

Expected: `isDraft: false`, public URL `https://github.com/RubenVanDerVeen/klad/releases/tag/v0.4.0`.
